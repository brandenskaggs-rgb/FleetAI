# Fleet AI code and dashboard audit

Date: September 8, 2026. Branch: `clean-auth-rebuild`.

## Scope and confidence

This was a risk-first repository audit and repair pass, not a security certification or a claim that every line has been manually reviewed. The inventory contained 516 tracked files. Automated syntax checking covered 168 first-party JavaScript files. Focused manual tracing covered authentication, tenant boundaries, account provisioning, JSON persistence, tablet authorization and telemetry ingest, GPS, model consumption, operational records, and dashboard requests/navigation.

Generated dependencies, trained model binaries, local credentials, and build output were not treated as application source. No passwords were reset. No production records were created for testing. Android source and the pairing protocol were not changed. The earlier uncommitted `/index.html` compatibility fix was preserved.

## Remaining work and limits

1. **P1 before scaling replicas:** DVIR, dispatch, parts, and other legacy collections still depend on JSON. Revision checks protect the single Node process; they are not a distributed lock or a transaction across multiple replicas. Keep one writer and persistent storage until these collections move to database transactions.
2. **P1 provisioning consistency:** Account changes in PostgreSQL and the secondary JSON index are still separate commits at the route level. The adapter transaction prevents partial writes inside PostgreSQL, but does not create a transaction spanning both stores. A failed secondary write must be reconciled, not treated as permission to recreate an account.
3. **P1 ML evidence review:** The alternate synthetic-prior service in `fleet_ai/api/ml_service.py` still uses sample-count-based confidence and default-filled features; its missingness calculation is overly optimistic. Node's observation-based confidence cap helps the dashboard, but does not independently validate every Python/API output. Review units, missingness, elapsed operating time, and real failure labels before strengthening model claims. No retraining or artifact replacement was attempted here.
4. **Operational records:** These new read endpoints show database records. Older JSON-only maintenance history is not silently migrated or merged. Pagination, manual work-order editing/closure, and reconciliation deserve a separate tested change.
5. **GPS history:** Older samples that never stored location cannot be reconstructed. Recovery checks the latest 30 sensor samples per vehicle; a long location-only period is not a durable trip-history implementation. Dense GPS fleet polling should move to a dedicated indexed last-position store before large-scale deployment.
6. **Hardware and compliance:** Re-test actual Bluetooth/J1939 equipment, background operation, ignition-off behavior, offline backlog replay, and tenant reassignment on pilot hardware. Existing tests do not certify FMCSA/ELD compliance or safe coexistence with another vendor's hardware.
7. **Coverage limits:** Not every Python/Android line or public marketing page received a manual review. A production penetration test, backup restore exercise, multi-instance/load testing, and Play Store policy review remain separate tasks. Passing tests cannot establish that no bugs remain.

## Release handling

These changes do not require a new driver APK. Deploy the web/backend changes together; new location metadata only accumulates after the backend update. Back up the operational JSON volume and database before deployment, exercise login plus pairing/telemetry smoke against a test tenant, and monitor 409 conflicts and 503 retries. Do not automatically retry uncertain POST requests. No commit or push was performed during this audit pass.
